# Theorem Notes — Writing workspace and dynamic documents

**Design amendment 1.2 · November 28, 2026 · Proposed implementation authority**

Read `BASELINE-v1.1.md` first. This amendment supersedes the earlier visual layout wherever it treated the Notes sidebar and document as equally elevated panes. It adds a writing-specific composition, registered insertable blocks, live collection projections, a context-action surface, and a conditional BlockNote adoption plan. It does not relax first-class user-defined object classes, stable identities, scoped graph access, or artifact ownership.

## Use the accompanying references

- `reference.html`: self-contained browser prototype, recreated from the inline illustrations in the design conversation. Open it locally. Switch between Library and Writing, change the collection view, drag a card between status lanes or use the Table status selector, drag or click an Insert item, right-click a block or record, and toggle the theme.
- `library.png`, `writing.png`, `context-actions.png`, `writing-dark.png`: rendered captures of the reference. Match the spatial and material hierarchy, not the hardcoded sample data. The screenshots are a design reference, not evidence of production functionality.
- The prototype deliberately uses illustrative data and local DOM interactions, not BlockNote, TanStack Table, real RustyRed, or an actual agent. It has no production persistence. Some controls only show an explanatory placeholder. Do not vendor this demo as production code.

## 1. Material hierarchy and workspace modes

**Library mode** is the object-browsing surface: flat Capacities-style navigation; recognizable cards, collection filters, search, saved views; generous gallery width. The left object-type list comes from the authorized workspace projection, not all internal schema labels. The same class can be made available without being pinned. Built-in and custom classes remain peers.

**Writing mode** is a contextual composition for an open prose-capable document. Ground the global rail, left object navigation, and right tool shelf in the surrounding workspace material. Remove their independent card elevation, enclosing outlines and heavy seams. The document alone rises from that ground, with a subtle contact shadow and broad ambient shadow, quiet corners, and a slightly lighter paper surface. In dark themes use tonal elevation rather than a bright border. Preserve the chosen Theorem palette through semantic tokens for ground, paper, tool, selection and text; don't introduce an unrelated hardcoded white theme. Proposed initial desktop geometry: left navigation about 220–250px; right shelf about 240–270px; prose measure about 640–720px; wider blocks may expand within the paper. Tune from mounted application captures, not literal pixels of the reference.

The existing Dockview layout remains authoritative. Switch material/layout on effective surface role, not on a special-case class name. Do not remount an active editor just because the sidebar flattens or the inspector opens. Preserve cursor, selection, IME, undo, current document reference, draft, scroll and subscriptions. Library mode returns to the previous scope and position. Split panes, full-width apps/notebooks, narrow windows, mobile drawers and focus mode must remain usable; do not force every object into a prose column. Left and right rails independently collapse.

## 2. Editor decision — evaluate BlockNote, preserve document authority

Preferred candidate: BlockNote core with React integration. It offers custom block schemas, customizable side and slash menus, drag handles and formatting. Editor.js uses its own tool-defined JSON blocks and is not a Markdown-native solution to the same problem. Milkdown Crepe, already present in the previously inspected Notes branch, remains the fallback until the migration gate passes. Do not maintain two production write authorities.

BlockNote's own documentation explicitly labels Markdown import and export lossy: nesting and styles may not round-trip; its recommendation is its native JSON for lossless editor-specific storage. That does not mean Theorem should replace its canonical document store with BlockNote JSON. BlockNote state should be a projection/adapted editor state, not an independent durable source of truth. Inventory the actual current production document kinds, storage paths, serializers, editor transaction flow, block identity, Loro/CRDT or other concurrency contracts where applicable, and artifact reference representation before designing the adapter. Existing prior source observations are not verification of the current branch.

Two routes may coexist through the same existing document authority:

- **Actual Markdown files:** original bytes are canonical. Parse the supported subset to an editable block representation with source ranges and stable identity mapping. Use source-aware patches against a verified base revision, preserving untouched spans (line endings, whitespace, frontmatter, comments, footnotes, reference links, fences, math, directives, unfamiliar extensions). Unknown constructs get a preserved opaque/source block or an explicit source-editor route. Do not silently normalize a file on open, save unrelated blocks with a lossy whole-document export, or claim that HTML conversion solves losslessness. If a requested edit cannot be serialized within the supported dialect, refuse that edit in this projection or explicitly offer a format upgrade/export. External file edits must trigger conflict/rebase handling, not last-write-wins data loss. Stable IDs for raw Markdown must use the existing owner if available; an identity mapping must not silently drift after edits or reopen.
- **Theorem-native dynamic documents:** use the existing canonical block/document contract as durable authority. Map its blocks, typed references and operations to editor blocks. Represent custom content by registered type, stable block ID, version and typed payload/reference; never serialize live component instances or an iframe's runtime state as document truth. Markdown is a deterministic portable projection with meaningful fallbacks and, only where an existing supported extension contract permits, references to rich blocks. Distinguish a portable export from an exact native restore. Do not create a second document model or introduce Yjs as another authoritative persistence/collaboration layer just because BlockNote supports it.

Run the migration gate before selecting a production editor: same source fixture through existing editor and candidate; no-op open/save byte identity for Markdown; paragraph edit preserving unrelated spans; complex nested lists, tables, code fences, math, links, citations, embeds, unknown directives, Unicode/IME; move, undo/redo and reopen preserving block and artifact identity; concurrent agent/human changes and external file edits; missing renderer fallback preserving data; selected revision and history readback. Measure interaction latency, startup cost, memory and correctness on representative real files. If an adapter cannot preserve the contract, retain Milkdown for that path and extend it rather than silently lose data. Layout and dynamic collections are editor-independent and should not wait on a successful migration.

Check pinned package versions and licenses. BlockNote core is MPL-2.0; XL packages such as multi-column editing and AI features are dual-licensed GPL/commercial. Do not add XL dependencies without a license review. Theorem already has its own agent and export mechanisms.

Official references: [BlockNote import](https://www.blocknotejs.org/docs/features/import/markdown), [export](https://www.blocknotejs.org/docs/features/export/markdown), [format interoperability](https://www.blocknotejs.org/docs/foundations/supported-formats), [custom blocks](https://www.blocknotejs.org/docs/features/custom-schemas/custom-blocks), [side menu](https://www.blocknotejs.org/docs/react/components/side-menu), [licensing](https://www.blocknotejs.org/pricing), [Editor.js save](https://editorjs.io/saving-data/).

## 3. Insert shelf — registered blocks, not fixed buttons

Right shelf tabs: **Insert / Format / Style / Info**. Insert is a discoverable palette with labeled drag handles; clicking or using the keyboard also inserts at a valid selection. Format is selection-sensitive; Style controls presentation rather than mutating the class or document data; Info exposes object properties, collections, connections, origin and history using authoritative metadata. Use the existing inspector rather than a second metadata system.

The same effective block registry supplies the shelf, slash menu, context menu, agent insertion and programmatic insertion. Reuse existing note tools, editor/drop adapters, artifact registry and operation discovery after inspecting the current owners. A contribution includes a stable ID, label/icon, applicable document kinds, payload schema/version, insertion/serialization adapter, renderer and preview/fallback, capability/effect declarations. User/extension blocks use this same contract. Default contributions: text, page/link, image/file, code, equation, table, gallery, Kanban, calendar, Mermaid, working artifact, notebook and optionally registered specialized visual components. Only surface installed supported operations as available; no fake enabled controls.

On drag from shelf or object library, transfer a typed descriptor/reference, resolve a valid insertion position, show an unobtrusive drop indicator, validate the target and commit through the editor's normal operation/undo/save path. A reference drop links an existing object; insertion of a new block creates a new block identity. Moving an existing block retains its identity. Use editor-native drag mechanics for internal blocks; consider existing drag/drop dependencies or Pragmatic Drag and Drop for external shelf/board interactions. Avoid multiple handlers independently consuming the same drop. Keyboard and touch alternatives must exist.

## 4. Embedded collections — same objects, many views

An embedded collection block holds a collection or saved query reference, projection settings (view, chosen properties, filters, sort/group, width) and stable block identity. It does not copy all source records into the document, nor run a second store. A single class library, curated mixed-type collection, saved view, or embedded view can refer to the same canonical object identities. Query results and view settings are separate; changing view is not changing membership. Creating a new record from a filtered view must explicitly initialize the required matching properties or explain why it will not appear. For mixed-type views, validate shared grouping fields or expose a clear ungrouped state.

Reuse Theorem's installed TanStack Table version and existing table/field components. It supplies headless row models, filtering, grouping, sorting, selection and pagination; styling, cell editing, drag/drop, data writes and server query integration remain our responsibility. Keep record IDs as row IDs rather than array positions. Table, Gallery and Kanban share a scoped query/result model and canonical field/relationship operations. When a Kanban card moves to another status column, send a validated update to that record's status, not a reorder of copied client data. For large collections use server-side grouping/filtering/pagination when appropriate; never fetch every class first. Virtualize visible rows/cards where measured useful. Handle loading, denied, failed, stale and missing records honestly.

A dynamic document can hold prose, live project/experiment views, a notebook, and working artifacts; each is anchored to its owner and revision semantics. Opening an app in a document follows the same artifact runtime as Notes/chat. A removed embed does not delete its target. Historical document revisions should identify whether an embedded view is a pinned snapshot or a live query; don't present today's query results as historical evidence. Offline/unavailable renderer: meaningful read-only fallback, with no data loss.

See [TanStack Table](https://tanstack.com/table/v8/docs/overview), [grouping](https://tanstack.com/table/v8/docs/guide/grouping). Use the repo's existing major version, not an incidental upgrade to satisfy a demo.

## 5. Contextual actions — right-click as a capability surface

Carry over the graph's existing context-action pattern. Generalize its real command owner/registry rather than build isolated menus for every editor. A block, text selection, object card, collection record/row, graph node/edge and artifact may each expose applicable local operations and applicable agent operations. Example groups: Edit (insert, duplicate, move, format), Connect (link, open, add to collection, copy reference), Work with Theorem (ask about this, explain, find evidence, suggest improvements, inspect dependencies), plus class-specific registered actions. Do not make every menu item an LLM request. Preserve the browser's native context menu for ordinary text/links when there is no valid custom target; support a keyboard context-menu key/Shift+F10, an explicit block menu, escape and focus return, and touch equivalents.

Resolve context against stable target identity and observed revision: document ID, block ID and/or object ID, selection spans/text when applicable, collection/view scope, origin surface, active agent/thread and permitted references. Use the existing operation/approval gate, revalidate scope and revisions at execution, and carry receipts. Do not infer broad write authority from an open object. A question targets the object without editing it. A proposed edit goes through preview/approval when required; accepting the proposal invokes the same canonical mutation as manual editing. No stale selection overwrites. Prefer relevant scoped context to dumping the whole document or schema registry into the prompt. Actions can use existing agent delegation, code mode or tool discovery; do not install one model tool per object or context menu item.

## 6. Delivery sequence and acceptance

Use the current branch, not the outdated screenshot-only implementation. Inspect canonical document storage and the current graph context menu, note editor/toolbox/drop code, artifact adapters, records/schema owner, existing TanStack Table and shell/Dockview. Reuse owners and existing components. The following requirements supplement the v1.1 gates; all must be exercised in the actual mounted application, not just this reference.

| ID | Obligation | Evidence |
|---|---|---|
| W01 | Library and writing roles apply correct materials and preserve editor continuity. | Before/after captures at matched viewport/zoom; edit a draft, toggle mode/rails, restore selection/scroll/undo; light/dark/narrow. |
| W02 | BlockNote only becomes a production adapter after the per-kind round-trip gate. | Real Markdown and native fixtures, persisted readback, conflict and unsupported-syntax cases. No-op raw Markdown save must not rewrite bytes. |
| W03 | Registered blocks appear through shelf, slash menu, keyboard and agent. | Install one unforeseen block without hardcoded menu changes; insert via actual drop and command, undo, reopen. |
| W04 | Embedded views use one record identity and canonical queries. | Create an unforeseen user class and several records; embed its view; update a row in Table, move a card in Kanban, verify Gallery and standalone library reflect the same committed record. |
| W05 | Collection and embed operations respect ownership. | Remove embed without deleting target; verify membership, filters, source state and historical pinned/live distinction. |
| W06 | Context actions share the existing capability owner. | Right-click text/block/row/graph node; ask a question with only scoped target; preview an edit, verify authorization and stale-revision refusal; perform with keyboard. |
| W07 | Artifact continuity and safe fallbacks. | Embed an existing saved artifact; compare identity and revision with Notes/chat; missing renderer retains readable reference and source data. |
| W08 | Query and rendering boundaries stay scoped. | Inspect request traces for a selected class/collection and focused inspector; no unrelated class scans or gallery-wide app starts. |
| W09 | Production verification, not a mock. | Capture actual running application and matching source revision; run relevant integration tests. Record unresolved failures explicitly. |

**Central acceptance journey:** create a new user-defined Benchmark experiment class at test time. Create a Page, open Writing mode, and write a paragraph. Insert a live collection by dragging from the shelf, switch Table/Kanban/Gallery, update an experiment from the board, observe the change in the standalone library, right-click the changed record and ask Theorem about its evidence. Insert a saved working artifact, collapse both sidebars and return without losing draft state. Save and restart. Confirm both the document's blocks and canonical referenced objects survive, then verify Markdown compatibility for an existing file separately. None of this should require a source-code change for the newly invented class.

## Implementation caution

This amendment is a design and technical proposal, not a new source review or a migration proof. The prototype uses ordinary HTML/CSS/JS solely to communicate behavior and appearance. The current storage, editor and graph-action implementation must be verified before adopting an adapter. Do not rewrite the database, introduce an independent ontology, duplicate artifact runtime, or couple visual polish to an unproven persistence migration.
